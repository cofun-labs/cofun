# Security model

What Cofun protects, from whom, and how. It describes the design, not a list of bugs: a weakness that can be used is [reported privately](../SECURITY.md) and fixed, not written here. The trade-offs the design accepts on purpose are named, with the reason for each. Where a guarantee is enforced, the code says how; this file says what must hold.

A change that touches one of the areas below is checked against this file, and updates it in the same PR when it changes what is said here (see [Rules for later changes](#rules-for-later-changes)).

## What is protected, and from whom

- **The user's Notion workspace**: what it says, that it changes only as the user wants, and the account's standing with Notion (the tools call Notion's internal API as the user).
- **What is on the device**: chats (which hold what the agent read), the sign-in, and the user's own model keys.
- **The account and its credits**: nobody else reads them or spends them.
- **The operator's side**: the hosted model's cost, the Stripe, Clerk, and Cloudflare accounts, and the right to publish the extension.

| Who | What they control |
|---|---|
| Someone who can put text where the agent reads it | A page shared with the user, a block or row they can edit, a title, a comment, a search result, a web page. They need no Cofun account and no access to the user's machine |
| A website the user visits | Its own pages, the cross-origin requests a browser makes from them, and its tab's title and URL |
| A signed-in Cofun user | Their own session token: any request to the worker under their own account |
| Anyone on the internet | Requests to the worker's routes that need no session |
| A contributor to the public repository | Issues, comments, and pull requests from forks |

Outside the model: someone who already has the user's Chrome profile (the privacy pages say what is kept there, unencrypted), and Notion, Clerk, Stripe, Cloudflare, or a model provider being compromised themselves. Dependencies are limited by the lockfile, dependency review in CI, and Dependabot.

## The agent

The agent loop and its tools run in the side panel. The model sees the system prompt, the conversation, and what the tools return; it acts only through the tools.

- **Text the user did not write is data.** Whatever a tool returns from Notion, another site, a web page or search, or a selection sent with "Ask Notico" is marked as data for the model, and written so it cannot pass for the tool's own notes. This guides the model; it does not bind it, which is why the limits below are in code.
- **What the model can do is the tool list.** Each tool's arguments are parsed before anything runs. In Read only, a call of a tool that changes data is refused in code before its preview or run (the tools are still offered, so every request starts the same and the prompt cache holds). Moving pages to the trash asks the user each time, naming each page. Saving a chat to Notion, and clipping a page to Notion from the context menu, are the user's own actions, not tools: Read only, which limits the model, doesn't apply to them.
- **Nothing the model writes makes a request to a host it chose**, but for the web pages it reads ([below](#accepted-web-pages-at-any-address)). What the tools write into Notion is text, and links a reader must click; nothing written makes Notion or a reader's browser fetch an address by being looked at. In the panel, a reply is rendered with no HTML, and its images are never loaded.
- **Only the active tab, only on Notion.** Notion requests run inside the user's active Notion tab, to its own origin, after checking it is still on Notion, and follow no redirect.
- **General browser-tab reads require site access and a tab the user chose.** The agent reads the page in the current tab, or in a tab the user added to the chat, only on a site the user allowed in the side panel and in Chrome's own prompt, which Chrome takes only during the user's gesture, so the model can't grant a site. The tools take no address, only which added tab to read, so never a link found in a page. Nothing is sent to the site by default. The exceptions are listed here, and are the only code the lint rules let send requests from a tab of an allowed site, so a new one changes both: on a YouTube video's watch page (`@cofun/tools`'s `youtube/`), the tab asks its own origin, with the user's YouTube session, for the video's watch page and its transcript, as the page does when the user opens its transcript. An exception sends only fixed reads of what the tab shows, to the tab's own origin, each once, following no redirect, stopping on a Stop or an answer it doesn't understand, and the model chooses nothing in them. The privacy pages describe this as a kind of request to a site the user allowed, without naming each site. The page reaches the panel as inert HTML, where no script runs and nothing loads, and its links are kept without their fragment, which can carry a token.
- **A web page at any address, and a web search with any query**, through the worker ([accepted below](#accepted-web-pages-at-any-address)). A failure goes to the model as a source that wasn't read, unless the request was turned away, which stops the question ([AGENTS.md](../AGENTS.md), "Calling outside services").
- **One question is bounded**: it has caps on model turns, on failed tool calls, on pages per bulk call, and on Notion requests before the user is asked whether to go on. A rate limit from Notion or Confluence stops the question. Confluence requests are bounded by time, response size, and collection page size. Requests to either site are sent once.
- **What is read back from the device is parsed**: a saved chat that does not parse is never opened or sent to the model, and a kept long result is read only by a chat whose own results name it.

### Accepted: writes without approval

Apart from the trash, the agent changes Notion without asking first. Text it reads that the user did not write, in Notion or from outside it, can carry an instruction, and a model may follow it: it could change pages, move a private page under a shared one, or write what the user can see where someone else can read it; a comment or a mention also notifies other people. The user sees every change on its tool card, and Notion's page history can undo it, though not what someone read meanwhile. This is the product's main risk. It is stated to users in [Notico's README](../extensions/notico/README.md). Read only is the switch for a user who does not accept it: it stops changes to Notion, not what the web tools send out. [#348](https://github.com/cofun-labs/cofun/issues/348) records asking first instead, and [#388](https://github.com/cofun-labs/cofun/issues/388) narrows what runs unasked.

A link is the one way written content can carry data out: only when someone clicks it.

### Accepted: web pages at any address

The web tools read whatever address the model gives: one the user wrote, a link it found in a page or in Notion, or one it made up. This is the maintainer's decision, so the assistant can follow links and look things up on its own judgment, and it is an exception to rule 4 below. The cost: an address is a way out for data. An instruction in text the user did not write can have the model put what the user can see into an address, which reaches the address's host with nothing for the user to approve; the tool's card shows it afterwards. A link from a page the user is signed in to can carry a token in its query, which reaches its site the same way. What limits it: the worker reads only public addresses, with no cookie or credential (below), each address is shown on its card, and reads are rate limited per user.

### Accepted: web searches

The search tool sends the query the model writes, which may hold anything the conversation holds. This is an exception to rule 4 below: an instruction in text the user did not write can have the model put what the user can see into a query. What limits it: the query goes only to one provider fixed in the worker, never to a host the model or a page chooses, and the provider keeps no data of what it serves, so whoever planted the instruction can't read it there. The worker keeps and logs neither the query nor the results, each query is shown on its card, and searches are rate limited per user.

A user can choose in an extension's settings to search with DuckDuckGo instead (UC-NOTICO-PANEL-004, UC-CONFLUCO-PANEL-004), off until they switch it on and Chrome grants the access. Each search then opens DuckDuckGo's HTML results page in a background tab of the user's browser, on one host fixed in the code (`@cofun/tools`'s `duckduckgo/`), still never one the model or a page chooses, and reads it with a fixed script in the isolated world, which takes no argument from the model; the query reaches DuckDuckGo only as that page's address. The page loads as any the user opens, with their DuckDuckGo cookies and IP address, and its address, with the query, stays in the browser's history: DuckDuckGo states it does not store searches, but it is not bound to us as the worker's provider is, which is the user's own choice and is said where they switch it on and in PRIVACY.md. Nothing pretends to be the user beyond opening the tab: when DuckDuckGo asks to confirm a person is searching, the question stops and the tab stays open for the user, and the extension never answers the check or searches another way. The worker's rate limit does not apply to these searches; it guards only what costs the operator money. The page's HTML is parsed in an inert document, not trusted: a result that is not a web address with a title is left out, and the results are data for the model, as the worker's are.

## The extension

- **Permissions** are the ones the manifest lists, with host access to the worker, Clerk, and the sign-in's parent domain (`*.cofun.cc`, to see one Clerk cookie). Notico has host access to Notion. Other sites are optional host permissions, granted one site at a time when the user allows it. The tab tools never read a tab on a host the extension holds by install (the sign-in's hosts, and Notion in Notico, which its own tools read): no grant would be asked for it. A test pins them and the content security policy, so neither changes unnoticed.
- **No way into the extension's code from a page.** There is no content script, no `externally_connectable`, no web-accessible resource, and no message listener: a web page, Notion included, has no channel to the side panel or the service worker. What a page can reach is the model, as text a tool returns, or as text the user selected in it and sent with "Ask Notico", which only the extension's own pages can read and which is parsed when read. When the user clips it, it also reaches the Notion page the user chose, with no model in between: its main content, parsed into blocks as the agent's writes are (only web, mail, and Notion page links kept), its title, as the new page's title, and its address, linked only when it is on the web. A clip writes nowhere else, and only once the user picked the item on that page.
- **Code in the user's tabs** runs in Chrome's isolated world, out of the page's reach, and is fixed. In the Notion tab, the model's arguments reach it only as the body of a request to Notion's endpoints. In a Confluence tab, searches and other reads take checked arguments, and writes take their target and content from a direct user request or the file the user chose. On other tabs the code reads the page without taking a model argument, and sends the site nothing but the exceptions above. "Ask Notico" and "Clip page to Notion" give the extension the tab they were used in, once, to read the selection, or the page's main content; it does not count as allowing the site.
- **Which Confluence site**: there is no configured site. A question captures the current tab when it is sent and stays on it. An Atlassian Cloud wiki (`*.atlassian.net/wiki`) is known by its address. On a site the user allowed whose URL has the shape of a Confluence page, an isolated script reads only the `confluence-context-path` meta tag, and the page must sit under that path. A page can claim to be Confluence, but every request goes back to its own origin, which the user allowed through Chrome's prompt from the tool's card; a site allowed for reading tabs counts as allowed here too. A tab whose address is not shaped like a Confluence page is refused without asking; one that is, on a site not allowed yet, is asked about first, then refused if its head names no deployment path that contains it. Page references stay bound to their site.
- **Self-managed Confluence** uses the site's REST API from a top-level tab checked against the origin and deployment path its page named. The isolated script compares the expected URL, uses same-origin credentials, and refuses redirects. Search terms and any search space key come from the current user message. Other reads can use references and continuation offsets from validated results in the same question. Text, titles, links, and editor excerpts are data for the model. An editor excerpt is rechecked against the same document before it goes with the question.
- **Confluence Cloud** runs allowlisted GET requests for published pages, CQL search, page and space inspection, and the folders in the page tree on the `atlassian.net` tenant in its captured tab. It uses the same permission, origin, redirect and direct-search-input rules as self-managed Confluence. Validated cursors and pending discussion reads stay in the extension behind a continuation scoped to the same site, tab, tool request and question. Cloud allows writes only for published child creation, title updates, ordinary label changes, footer comments and replies, same-space moves and body-only copies, recoverable trash, published text edits, restoration, undo, and confirmed local attachment writes. It validates the page hierarchy and checks whether a move, copy, or trash action could drop access restrictions. Cloud restoration reads the fixed native confirmation page and submits only its expected same-origin form with the checked page and space. Its CSRF value stays inside the isolated tab. The result is verified through REST. Cloud attachment writes use the native same-origin action for the captured published page and are verified through REST. The confirmation explains that the native action matches attachments by filename and a concurrent same-name upload can receive a new version. Cloud publishing and edit undo use the service's draft reconciliation and may overwrite an unpublished draft, an accepted behavior. These use the same direct user intent and target verification as self-managed Confluence.
- **Confluence writes** take the operation and its content from the current direct user request. A local file is selected in the composer and requires confirmation. Trash and restore show the target and request approval when they would change it. Read only blocks every write tool before preview. Writes are bound to the captured tab, check published versions or relevant state before applying, and verify the result before reporting success. Copies reject unsupported or unsafe storage instead of reusing it. An uncertain write stops the question if its outcome is still unknown. For an uncertain edit, trash, or restore, including undo of an edit or trash action, Confluco may read the same page once to check the resulting version, content, or status. It reports success only when that read verifies the expected result. A definitive refusal such as sign-in required or rate-limited stops the question without a verification read. It never repeats the write. A chat can undo a new verified edit or trash action only while the expected site state still matches.
- **The page clips go to is the browser profile's, not a Cofun account's.** Its link and title are kept in Chrome's synced storage for the whole profile, as the "Ask Notico" switch is, and any Cofun account signed in there clips to it. It holds nothing of a Cofun account: it names a Notion page, which the Notion session of the same profile reads and writes, whoever is signed in to Cofun. A clip picked in the menu is handed to its window's side panel the same way as "Ask Notico" text, and dropped if no panel takes it within a minute. Turning Clip on with no page chosen makes a private page "Notico Clips" in the workspace of the Notion page open in the current tab, or takes the one already in the user's Private section: the one write Settings makes, sent once.
- **The content security policy** lets the extension's pages run only their own scripts and connect only to the hosts in its privacy page ([Notico](../extensions/notico/PRIVACY.md#where-data-goes), [Confluco](../extensions/confluco/PRIVACY.md#where-data-goes)). No remote code is loaded.
- **Module boundaries are lint errors** ([AGENTS.md](../AGENTS.md), "Architecture").
- **A user's own model** is asked from the extension directly: the key goes only to the service it belongs to, and so does the conversation, in place of the worker. What the worker section says does not apply to it; the provider is the user's choice.

### Accepted: nothing on the device is encrypted

Chats, the Clerk client token, and the user's model keys are kept in the Chrome profile, unencrypted; chats and keys stay after sign-out. A key kept in the same profile would not protect them from someone who has the profile. The privacy page says so.

## Sign-in and the worker

- **Every route under `/v1` needs a session.** The session check comes first in the `/v1` app, so a route cannot be added without it, and a test checks every route. The token is verified with Clerk's public key, with no call to Clerk, and a token issued to an origin must name an allowed one.
- **Authentication is the bearer token, never a cookie**, so a cross-origin page gains nothing by calling, and CORS can allow any origin.
- **A user reaches only their own account.** No route takes a user id from the request except the admin's.
- **Admin routes** need the `admin` role, which comes from Clerk metadata users cannot write, and a token issued to the worker's own origin. Everything else gets one and the same refusal. Hand grants are bounded and logged with the admin's id.
- **The model is the worker's choice.** A request naming another is refused, and only the fields the model needs are passed on.
- **Web pages the worker reads** are public only and never the worker's own: it sends no cookie or credential, and refuses our own domain, local network names, addresses given as an IP, and addresses with another port or a user name, at every redirect, and a Workers subrequest can't reach a private network. A page rendered in Browser Run is loaded by a browser outside these checks, with no session of ours, so what it can reach is what anyone can.
- **Web searches** go to one provider, fixed in the worker; the client chooses only the query and how many results.
- **What costs the operator money is charged and capped per user**: model calls, renders, and searches are charged in credits, go ahead only while the balance is above zero, and are rate limited, which also bounds what calls sent at once can cost beyond the balance. Model calls, which can run for minutes, are also capped by how many one user has going at once, and each is charged when the model is done, on the worker's schedule: a client that stops reading a reply neither delays its charge nor frees its slot. A paid call that failed costs the user nothing, so a user could have failing calls made at the operator's cost: accepted, bounded by the same limits (and, for a model looping in the extension, by the cap on failed tool calls in one question). A paid call is never retried.
- **Payments.** A Stripe event counts only with Stripe's recent signature. What is granted is what Stripe says was sold, for the user and pack the worker itself wrote on the checkout, and each payment grants once and is taken back once, in whatever order events arrive.
- **No content is stored or logged** ([PRIVACY.md](../PRIVACY.md)).

### Accepted: a session token that names no origin

A token with no `azp` passes the session check, though not an admin route's, because Clerk hands one to a side panel that just loaded. Refusing it would gain little: such a token, like one naming any origin, comes only from Clerk's Frontend API, which anyone holding the user's Clerk client cookie can ask outside a browser. A page in the browser cannot reach the Frontend API's answer at all, as long as two things stay true:

- **Clerk's Frontend API refuses an origin the instance does not allow** (another website, an extension it does not list, `null`). This is the Clerk instance's configuration, outside this repository.
- **No other host under `cofun.cc` serves code a browser runs** (rule 9 below), since every `cofun.cc` origin is one the Frontend API answers.

## Secrets and the repository

- **Nothing secret is committed** ([AGENTS.md](../AGENTS.md), "Public repository"): the worker's secrets live on Cloudflare.
- **`main` changes only through pull requests and a merge queue**, with every action pinned to a commit and GitHub's settings kept as code.
- **No workflow that reads untrusted text can push, and GitHub holds no deploy or store credential.** Cloudflare pulls the repository and deploys on merge; a person uploads the release zip to the store after checking its hash ([release.md](release.md)). The one secret on GitHub is Claude's token, held by the review workflow, which a fork's pull request can't reach and which can only comment.
- **The public media bucket under `cofun.cc` holds images and videos only** (rule 9).

## Rules for later changes

A PR is checked against these, beside the reviewer's list in [review.md](review.md).

1. **A new tool that changes data** says in its PR why it may run unasked, or asks first.
2. **A new kind of writable content** (a block type, a property type, an icon or cover by URL) is checked for whether Notion or a reader's browser fetches an address in it without a click. If it does, the model must not be able to choose that address.
3. **A new source of text for the model** (another site, a file, a search, an outside service) is untrusted from its first PR: marked as data for the model, and with a rule for which changes still run unasked once the conversation holds it.
4. **A request to an address, or with arguments, the model writes** (a fetch, a search, a call to an outside service) is a way out for data. It needs a rule in code for what is allowed, checked against the user's own messages, not the model's. An exception is accepted in this file, as the web tools are above.
5. **A new host** changes the content security policy, its test, and the privacy page's table together.
6. **A new way into the extension** (a content script, a message listener, `externally_connectable`, a web-accessible resource) treats what arrives as untrusted, and is described here.
7. **A new route on the worker** goes under `/v1` unless it has its own proof of who is calling, as the Stripe webhook has, and takes a user id from the request only on an admin route.
8. **Anything that costs the operator money** is charged or capped per user before it is offered.
9. **Nothing a browser runs is served from another host under `cofun.cc`.**
10. **A weakness that can be used is not written into a public Issue, PR, or this file.** A weakness only a PR brings in, not yet merged, may be described in that PR, so it gets fixed. A usable one goes to the maintainer privately ([SECURITY.md](../SECURITY.md) says how), and this file changes when the design does.
